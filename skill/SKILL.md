# 仕様駆動開発（Spec-Driven Development）

目的は、開発の整合性を保ち、何をなぜ作ったかを明白（ホワイトボックス）にすることである。仕様にない作業を禁止する仕組みではない。突発的なバグ修正などは spec を経ずにコードを変更してよい。ただし、その変更が既存 spec の要件・設計と食い違うなら、同じ変更の中で該当 spec を更新する（仕様と実装の乖離は、後から誰も気づけなくなるため）。

機能の追加・修正では、`specs/<component>/` に次の3ファイルを整備してから実装する。合否は **`spec-lint` の結果だけ** で判定する。レビュー担当（人間か AI か）で基準が変わると、同じ仕様書の評価が揺れるためである。

| ファイル          | 役割                             | 更新契機                         |
| ----------------- | -------------------------------- | -------------------------------- |
| `requirements.md` | 何を実現すべきか（要件）         | 仕様変更時のみ                   |
| `design.md`       | それをどう実現するか（設計）     | 設計変更時のみ                   |
| `tasks.md`        | 具体的に何をするか（作業と検証） | 作業のたびに（チェックボックス） |

依存は一方向で、`tasks.md` → `design.md` → `requirements.md` とする。実装や作業の都合で要件・設計を歪めない。

## 進め方の方針: 基本は自走する

このスキルの手順は、利用者への確認を挟まずに最後まで進めてよい。判断が要る場面でも、まず仕様書・既存コード・PoC の結果から根拠のある案を選び、選んだ内容と理由を最後の報告に書く。

確認のために止まるのは、次のように「どちらを選ぶかで作るものが変わり、根拠からは決められない」ときだけである。

- PoC の結果が、事前の調査（仮説・合格基準）と食い違い、構想や方針の変更を要するとき。
- 要件の目的や対象範囲そのものを変える判断が必要なとき。
- 履歴に入っていない PoC を削除するときなど、取り返しのつかない操作を伴うとき。

## 手順

1. 対象の `specs/<component>/` を確認する。なければ `templates/` の3ファイルをコピーする。要件は確定しているが設計・実装に着手しない機能は、`requirements.md` だけを置く（「要件のみ」。設計に着手するとき design.md と tasks.md を両方追加する）。
2. 雛形の記入例を対象の内容に置き換える。見出し・行形式は変えない（検査が行形式に依存するため）。
3. `spec-lint <component>` を実行し、指摘が 0 件になるまで本文を直す。指摘の意味は `references/rules.md` にある。合格後、設計に図があれば「図の目視確認」を 1 回行う（`references/diagrams.md`）。
4. spec の追加・削除や、構成要素・技術基盤・制約値の変更を伴い、設計済み spec が閾値（初期 3 件）以上なら、同じ変更の中で `docs/architecture.md` を更新する（`references/workflow.md`）。
5. 要件・設計に未確定の点があれば、上の方針に沿って決め、結論を本文に反映してから完了とする。未確定のまま残す書き方は spec-lint が弾く（W001）。

## spec-lint

```sh
spec-lint                 # 全件を検査する（specs・docs/architecture・poc）
spec-lint <spec名>        # 対象を絞る。architecture、poc/<テーマ> も指定できる
spec-lint --json          # 機械可読な出力
spec-lint --status        # spec・PoC・architecture の工程を成果物から導出して表示する
spec-lint --format        # 整形の指摘（P001）を prettier で書き直す。検査だけ省くなら --no-format
```

終了コードは 0=指摘なし／1=指摘あり・依存の不備／2=引数エラー・設定エラー。同じ入力には常に同じ出力を返す。`--root <dir>` で specs ルートを変えられる。`spec-lint` が見つからないときは `references/setup.md` で導入する。Markdown の整形も spec-lint が検査する（P001）。

閾値などの数値は、リポジトリ直下の `.spec-driven.json` で調整できる（`references/workflow.md` 9 節）。

## 参照先

必要になった時点で読む。上の手順だけで足りるときは読まなくてよい。

| 知りたいこと                                                              | 読むもの                          |
| ------------------------------------------------------------------------- | --------------------------------- |
| ディレクトリ規則、ID とトレーサビリティ、3ファイルそれぞれの書き方の原則 | `references/spec-rules.md`        |
| design.md の関係図・ワークフロー図の規則と、図の目視確認                  | `references/diagrams.md`          |
| UI を含む Phase の検証（Playwright）                                      | `references/ui-verification.md`   |
| architecture.md（1 ファイルとくくり別）と PoC の手順・判断基準・設定      | `references/workflow.md`          |
| 個々の検査ルール（ID と意味）                                             | `references/rules.md`             |
| spec-lint とスキルの導入・更新、CI への組み込み                           | `references/setup.md`             |
| 雛形（記入例。そのままチェックを通過する）                                | `templates/`                      |

## 開始時のスキル更新

作業に着手する前に、最初に 1 回だけ、スキル自身を最新にする（同じ会話の中では繰り返さない。利用者が更新しないよう指示したときは行わない）。

1. スキルのディレクトリ（この SKILL.md があるディレクトリ。symlink は `realpath` で実体を辿る）が git の作業ツリーの中なら、`git -C <スキルのディレクトリ> pull --ff-only` を実行する。
2. 失敗した（未コミットの変更、履歴の分岐、ネットワーク不通）ときは、強制せず（`reset`・`stash`・`--force` を使わない）、理由を 1 行で伝えて現在の版のまま続ける。
3. git の作業ツリーでないときは、更新しないことを 1 行で伝えて続ける。

`spec-lint` の更新は `references/setup.md` に従う。
