# spec の書き方の原則

`specs/<component>/` の構造と、3ファイルそれぞれの書き方の原則である。個々の検査ルールは `rules.md` にある。ここには、検査の背後にある理由を書く。理由を知っていれば、ルールの文面に載っていない場面でも同じ方向に判断できる。

## 1. ディレクトリ規則（S系）

- **1ディレクトリ = 1コンポーネント**。実装上のまとまり（例: `notification-api`、`delivery-worker`）ごとに `specs/` 直下へ作る。1コンポーネントに複数の FR を含めてよいが、FR が複数コンポーネントにまたがる場合はコンポーネントごとに分割する。担当が分かれる単位と仕様の単位を揃えると、変更の影響範囲が spec 1 つに収まるためである。
- **階層を作らない**。`specs/<component>/` の下にサブディレクトリや3ファイル以外を置かない。`requirements.md` は必須で、`design.md` と `tasks.md` は両方置くか両方置かない（両方なしは「要件のみ」の spec）。置き場所が一意なら、探す手間も、置き場所の議論も生まれない。
- **他 spec と関係を持たせない**。他 spec への言及は `requirements.md` の「3. 前提」に `- 前提: <spec名> — <理由>` の形式でのみ書ける（2件以内）。前提先の spec 自身は前提を持てない（連鎖・循環の禁止）。design.md・tasks.md からは他 spec に一切言及しない。spec 同士が絡み合うと、1つを読むために他を全部読む必要が出て、独立して変更できなくなる。
- 全タスクが完了（`[x]`）した spec は、次を満たさなければならない（仕様と実装の乖離を検出するため）。
  - design.md の構成表のパス、tasks.md の検証行・E2E 行のテストファイルが実在する。
  - すべての受け入れ条件 `AC-n` について、`tests/` 配下にテスト名へ `<spec名>/AC-n` を含むテストが存在する（例: `test("notification-badge/AC-1: 未読3件で「3」を表示する", …)`）。
  - 構成表のパスがすべて存在しない spec は、実装が除去された dead spec とみなし、spec ディレクトリごと削除する（S009）。

## 2. ID とトレーサビリティ

```
FR-n / NFR-n ──(受け入れ条件)── AC-n (FR-m)
      │
      └──(設計項目の見出しタグ)── ### D-n: <題> (FR-m, NFR-k)
                                        │
                                        └──(Phase の対応行)── - 対応: D-n   ※各 D はちょうど1つの Phase
                                                                └── - [ ] T-p.m: <作業>
```

- ID はファイル内で1からの連番とし、欠番を作らない。
- 対応関係は上図の位置（AC の括弧・D 見出しのタグ・Phase の対応行）でのみ表す。本文中で ID や他の仕様書ファイル名に言及しない。参照の網を作らないことで、各文書を上から順に一度読めば理解できる状態を保つ。

## 3. 各ファイルの原則

### requirements.md

- 「現状の実装がどうなっているか」に依存しない書き方をする。新機能と既存機能の改修で文体・粒度を変えない。要件が実装の現状に引きずられると、本来満たすべきことと現状の追認が区別できなくなる。
- 実装の詳細（ファイルパス・関数名・バッククォート）を書かない。受け入れ条件からの `tests/` パス参照のみ許可する。実装の詳細は design.md の責務である。
- FR／NFR／AC は1行1文で書く。NFR は数値を含めて定量的に書く（達成したかを誰が見ても同じに判定できるようにするため）。

### design.md

- 方針が確定していることを前提とした文書であり、実装状況の整理表・先送りの記述を書かない。判断を実装時の裁量に委ねると決めたなら、「委ねる」という方針自体を書く。
- 各設計項目（D）は、関数シグネチャ・データ構造・疑似コード・シーケンスのいずれかをコードブロックまたは表で示し、ソースコードの水準まで具体化する。曖昧な設計は、実装者ごとに異なる解釈を生むためである。
- 「2. 関係図・ワークフロー」に、構成要素の依存を示す**関係図**と、処理の流れ・状態遷移を示す**ワークフロー図**を mermaid で書く（`diagrams.md`）。構成表が3行以下の spec のみ「- なし」で免除できる。

### tasks.md

- 実装状況の追跡はチェックボックスに一本化する。進捗の情報が複数の場所にあると、必ずずれる。
- 新たな仕様判断・設計判断をここで行わない。疑問が生じたら requirements／design に立ち返って更新する（依存の向きを守るため）。
- Phase は実行順に5個以内とし、細分化しない。各 Phase は「対応 → タスク → 検証 →（E2E）」の固定形とする。

## 4. スクリプトで判定できない観点

次の観点は機械判定できないため、仕様書の作成・更新時に目視で確認する。

- 要件が目的を過不足なく満たしているか。対象外に書いた事項が FR に混入していないか。
- 設計項目が要件を実際に実現できる内容か（タグが付いているだけでないか）。
- タスクの順序で実装した場合に、各 Phase の検証が単独で成功するか。
- 図が設計項目と矛盾していないか（`diagrams.md` の「図の目視確認」の 5 項目で確認する）。
